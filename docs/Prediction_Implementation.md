## Поток данных

| Этап | Реализация | Источник истины |
|---|---|---|
| Клиент нажимает Shift | ALabCharacter::SprintPressed | Только намерение пользователя |
| Предсказание | bWantsSprint, GetMaxSpeed: 900 см/с на земле | Предварительная локальная симуляция |
| Сохранение | FSavedMove_Lab::SetMoveFor, FLAG_Custom_0 | Сохранённое намерение, не разрешение |
| Передача | Штатный ServerMove/packed movement CMC | Клиентский ввод и данные штатного хода |
| Серверная симуляция | UpdateFromCompressedFlags, GetMaxSpeed | Режим движения и правила сервера |
| Ответ | Штатное подтверждение/ClientAdjustPosition CMC | Позиция и скорость сервера |
| Повторное проигрывание | CMC + FSavedMove_Lab::PrepMoveFor | Неподтверждённые ходы с учётом запрета |
| Чужой персонаж | ReplicatedMovement и сетевое сглаживание | Авторитетные обновления сервера |

Штатные ServerMove содержат также клиентскую позицию для сравнения. Она не является
командой установить позицию: CMC воспроизводит движение и проверяет расхождение.
Наши RPC не принимают координат, скорости или клиентского времени.

## Роли классов

| Компонент | Ответственность |
|---|---|
| LabGameMode, только сервер | Выбирает класс Pawn/HUD; штатный GameMode создаёт игроков в PlayerStart |
| Стандартный PlayerController | Владение Pawn, ControlRotation, маршрутизация локального ввода и RPC владельца |
| LabCharacter | BindAxis/BindAction, камера, переключение режимов, baseline RPC, сообщения и время реакции |
| LabMovement | Скорость, распаковка флага, авторитетные ограничения, создание prediction data |
| FSavedMove_Lab | Запись и восстановление спринта; запрет объединять ходы с разным флагом |
| LabHUD | Наблюдение роли, скорости, режима, отклика |

Привязки ввода сделаны на Character через InputComponent; отдельный подкласс
PlayerController для этого небольшого прототипа не требуется.

## Действие и проверки

Спринт увеличивает скорость на земле с 450 до 900 см/с. В воздухе используется
обычная логика CMC без ускорения спринта. Коллизии, ускорение и допустимость движения
рассчитывает CMC. Выносливость и кулдаун не входят в правила выбранного действия.

Сервер независимо проверяет: Pawn существует и принадлежит вызвавшему RPC клиенту
(стандартные правила ownership Unreal); MOVE_Walking; отсутствие приседания;
собственный bServerSprintLocked. Итоговая скорость задаётся серверной константой.
Baseline-запрос дополнительно отклоняется вне земли; RPC получает лишь bool и ID.
Запрос baseline не даёт бессрочное разрешение: каждый последующий ход снова ограничен GetMaxSpeed.
Серверная проверка позиции и времени CMC не отключается.

В CMC flag Custom_0 обозначает желание спринта. Он записывается в SetMoveFor,
отправляется GetCompressedFlags, принимается UpdateFromCompressedFlags и восстанавливается
PrepMoveFor при replay. CanCombineWith запрещает объединение начала/конца спринта.
Clear удаляет старое значение при повторном использовании объекта хода.

После replay ClientUpdatePositionAfterServerUpdate восстанавливает текущий живой
флаг спринта: исторические флаги нужны только при проигрывании SavedMoves, иначе
старый спринт мог бы «залипнуть» после отпускания клавиши. Серверный запрет при этом
не откатывается. Метрика baseline дополнительно требует актуального подтверждения RPC.

## Сравнение вариантов

При CSP ON флаг меняется сразу: движение локально ускоряется до ответа сервера.
CMC сохраняет и отправляет ввод, сервер воспроизводит его самостоятельно.

При CSP OFF только **пользовательское действие** ожидает подтверждения. Клиент
посылает ServerBaselineSprint, сервер проверяет запрос и вызывает ClientBaselineSprint;
только актуальный ответ с совпадающим ID устанавливает флаг на владельце. Дальше
намерение проходит тот же CMC-путь. Устаревший ответ после отпускания Shift игнорируется.
Это намеренно консервативный baseline с дополнительным ожиданием разрешения; отдельная
серверная симуляция по RPC не запускается параллельно с ходами, чтобы не получить двойной эффект.
Обычная ходьба в обоих режимах остаётся предсказываемой.

При задержке 100 мс в каждую сторону ожидание RPC-ответа порядка RTT ≈ 200 мс
плюс обработка и разгон. Это **ожидание**, не измеренный результат.
При CSP задержка локального старта обычно ограничена кадром и разгоном.
HUD/log измеряет время от нажатия до скорости >475 см/с; это не чистая длительность
сетевого обмена. Перед каждой попыткой удерживать W до стабильных 450 см/с,
затем нажимать Shift. Делать не менее 10 попыток каждого режима на одном профиле.
Не смешивать отказы и успешные активации. Неуспешная попытка не создаёт событие response.

## Намеренное расхождение

В режиме CSP ON без Shift нажать F3 на клиенте и подождать секунду:
сервер устанавливает запрет, не сообщая о нём владельцу заранее. Затем W + Shift.
Клиент ожидает 900 см/с, сервер оставляет 450 см/с. При обнаружении флага сервер
пишет server_reject и посылает ClientSprintPolicy(true). Владелец узнаёт запрет.
CMC независимо сверяет позицию и отправляет настоящую позиционную коррекцию;
сохранённые ходы воспроизводятся с серверным запретом. PrepMoveFor восстанавливает
намерение, но не восстанавливает старое разрешение, поэтому replay сходится к 450.

ClientSprintPolicy сам не перемещает персонажа: это доставка игрового правила.
Позиционная коррекция — отдельная встроенная процедура CMC. Для T5 нужно зафиксировать
её маркеры `p.NetShowCorrections 1` и строки LogNetPlayerMovement, а не только отказ RPC.
При малом расхождении коррекция может не потребоваться из-за допусков CMC; повторить
на профиле Loss175, сохранив кадры и лог реальной коррекции. Отпустить Shift и нажать
F3 повторно для снятия запрета. RPC F3 — только учебный инструмент, не игровое право клиента.

## Сетевая эмуляция

play.ps1 задаёт исходящую эмуляцию **на обоих процессах**, входящая остаётся нулевой.
Один пакет проходит задержку один раз; не добавлять одновременно такой же incoming lag.

| Профиль | Команды на хосте и клиенте | Ожидание |
|---|---|---|
| Clean | PktLag 0; PktLagVariance 0; PktLoss 0 | Без искусственной задержки |
| Lag100 | PktLag 100; PktLagVariance 0; PktLoss 0 | 100 мс в сторону, RTT около 200 мс |
| Loss175 | PktLag 175; PktLagVariance 25; PktLoss 5 | 150–200 мс в сторону, 5% исходящих потерь |

Имена консольных команд имеют префикс `NetEmulation.`. Они передаются через ExecCmds.
Параметры сверены с документацией Epic; фактические строки `PktLag set to`,
`PktLagVariance set to`, `PktLoss set to` присутствуют в логах каждого процесса.
5% применяется к пакетам
каждого направления; это не означает ровно 5% потерянных игровых действий.
Надёжные RPC переотправляются, но на потерях могут дольше ждать доставки.

## Проверка и ограничения

Исходники: [LabCharacter](../Source/PredictionLab/LabCharacter.cpp),
[LabMovement](../Source/PredictionLab/LabMovement.cpp), [Saved Move](../Source/PredictionLab/LabMovement.h).
Испытания: [T1–T5](Prediction_Test_Matrix.md). Доказательства: [media](media/README.md).
Подписанные нативные скриншоты и исходные журналы находятся в docs/media.
Вместо видео используется разрешённая методичкой серия скриншотов; подписи и значения
времени реакции приведены в media/README.md. Численные результаты рассчитаны из реальных
событий response; cmc_correction пишет действительный callback движка,
а счётчик replay увеличивается внутри PrepMoveFor. Сборка Editor и Game, cook/stage/archive
завершились успешно. Факт работы на конкретном ноутбуке нужно проверить после переноса.

Проект использует геометрического персонажа и собственную арену с устройством Third Person,
а не скопированные бинарные ассеты Epic Third Person Template. Если преподаватель требует
именно шаблон, создать C++ Third Person в UE 5.8, добавить модуль и выбрать LabGameMode;
также сохранить сгенерированную карту и ссылку на фактический коммит перед сдачей.
Нет анимации, matchmaking, dedicated server target, античита и нагрузочных испытаний.
Серверная блокировка асинхронна; до её получения клиент может кратко ошибаться — это предмет опыта.
